Lab Focus

Automating Docker container builds, layer caching, and secure container image delivery to Amazon ECR on every git commit.

1. CI Objectives & Core Principles

Continuous Integration is the discipline of validating and packaging code on every merge so that deployment artifacts are always pre-built, tested, and ready for release. In Phase 3, our CI stage produces production container images and publishes them directly to Amazon ECR.

A production-ready CI pipeline adheres to four golden rules:

1. Immutable Artifacts

Every single build produces an image tagged with the exact 40-character Git commit SHA. You can always trace a running container back to the exact commit that generated it.

2. Layer Caching

Builds must not compile dependencies from scratch on every run. GitHub Actions Buildx caching (type=gha) cuts build durations from minutes to seconds.

3. Path Filtering

Commits modifying only documentation or Terraform manifests should never trigger resource-intensive Docker image builds.

4. Clean Job Outputs

The build job passes the resolved registry URI and image tag downstream to the deployment job via outputs.

2. Event Triggers & Path Filtering

Without path filters, updating a README.md or adding a diagram causes GitHub Actions to rebuild and push entire multi-hundred-megabyte Docker images to ECR. Because directory wildcards like phase2/** match every file inside those directories, we must explicitly exclude documentation using negative patterns (prefixed with !). We enforce fine-grained triggers in .github/workflows/deploy.yml:

.github/workflows/deploy.yml YAML 
on:
  push:
    branches:
      - main
    paths:
      - 'phase2/**'
      - 'phase3/**'
      - '.github/workflows/**'
      - 'Dockerfile'
      - 'docker-compose*.yml'
      - '!**/README.md'
      - '!README.md'
      - '!**/readme.md'
      - '!readme.md'
  workflow_dispatch:
    inputs:
      environment:
        description: 'Target deployment environment'
        required: true
        default: 'production'
      tag_override:
        description: 'Custom tag override (optional)'
        required: false
        default: ''

3. Concurrency & Race Condition Prevention

What happens if two developers push commits 10 seconds apart? Without concurrency control, both workflows run in parallel. A slower build from an earlier commit could deploy after the newer commit, reverting production to stale code.

We add a queue group so jobs execute serially:

concurrency block YAML 
concurrency:
  group: production-deployment
  cancel-in-progress: false

Setting cancel-in-progress: false ensures every production rollout finishes cleanly before the next queued rollout begins.

4. Docker Buildx & GitHub Actions Layer Cache

Docker Buildx leverages BuildKit under the hood. Standard Docker builds on CI throw away intermediate layer caches between runner runs. By setting cache-from: type=gha and cache-to: type=gha,mode=max, BuildKit persists unchanged npm ci layers inside GitHub's caching backend:

build-push-action configuration YAML 
- name: Set up Docker Buildx
  uses: docker/setup-buildx-action@v3

- name: Build & Push Backend Image
  uses: docker/build-push-action@v5
  with:
    context: ./phase2/backend
    file: ./phase2/backend/Dockerfile
    push: true
    tags: |
      ${{ steps.login-ecr.outputs.registry }}/zeetafin-backend:${{ steps.set-tag.outputs.tag }}
      ${{ steps.login-ecr.outputs.registry }}/zeetafin-backend:latest
    cache-from: type=gha
    cache-to: type=gha,mode=max

5. Authenticating to Amazon ECR in CI

Amazon ECR does not accept raw AWS Access Keys directly via docker login. ECR requires exchanging your IAM credentials for a short-lived authorization token (valid for 12 hours). The official AWS actions handle this handshake automatically:

AWS Actions ECR Auth Step YAML 
- name: Authenticate with AWS
  uses: aws-actions/configure-aws-credentials@v4
  with:
    aws-access-key-id: ${{ secrets.AWS_ACCESS_KEY_ID }}
    aws-secret-access-key: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
    aws-region: ${{ secrets.AWS_REGION || 'us-east-1' }}

- name: Log in to Amazon ECR
  id: login-ecr
  uses: aws-actions/amazon-ecr-login@v2

Once amazon-ecr-login completes, steps.login-ecr.outputs.registry contains your full AWS account ECR URI (e.g. 123456789012.dkr.ecr.us-east-1.amazonaws.com).

6. Dual Tagging: Commit SHA vs. Latest

A classic DevOps anti-pattern is deploying solely with the :latest tag. If something breaks in production, what commit broke it? How do you roll back?

We implement a dual-tagging strategy:

  • :${{ github.sha }}: The immutable release artifact. Never overwritten. Provides perfect traceability.
  • :latest: The rolling convenience tag. Updated on every successful build to point to the most recent mainline commit.

7. The Build Job Manifest

Here is the complete, isolated build-and-push job definition that powers the first stage of .github/workflows/deploy.yml:

build-and-push Job Snippet YAML 
build-and-push:
  name: Build & Push Images to Amazon ECR
  runs-on: ubuntu-latest
  outputs:
    ecr_registry: ${{ steps.login-ecr.outputs.registry }}
    image_tag: ${{ steps.set-tag.outputs.tag }}

  steps:
    - name: Checkout Application Code
      uses: actions/checkout@v4

    - name: Set Image Tag
      id: set-tag
      run: |
        if [ -n "${{ github.event.inputs.tag_override }}" ]; then
          TAG="${{ github.event.inputs.tag_override }}"
        else
          TAG="${{ github.sha }}"
        fi
        echo "tag=${TAG}" >> "$GITHUB_OUTPUT"

    - name: Set up Docker Buildx
      uses: docker/setup-buildx-action@v3

    - name: Authenticate with AWS
      uses: aws-actions/configure-aws-credentials@v4
      with:
        aws-access-key-id: ${{ secrets.AWS_ACCESS_KEY_ID }}
        aws-secret-access-key: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
        aws-region: ${{ secrets.AWS_REGION || 'us-east-1' }}

    - name: Log in to Amazon ECR
      id: login-ecr
      uses: aws-actions/amazon-ecr-login@v2

    - name: Build & Push Backend Image
      uses: docker/build-push-action@v5
      with:
        context: ./phase2/backend
        file: ./phase2/backend/Dockerfile
        push: true
        tags: |
          ${{ steps.login-ecr.outputs.registry }}/zeetafin-backend:${{ steps.set-tag.outputs.tag }}
          ${{ steps.login-ecr.outputs.registry }}/zeetafin-backend:latest
        cache-from: type=gha
        cache-to: type=gha,mode=max

    - name: Build & Push Frontend Image
      uses: docker/build-push-action@v5
      with:
        context: ./phase2/frontend
        file: ./phase2/frontend/Dockerfile
        build-args: |
          NEXT_PUBLIC_API_URL=http://${{ secrets.EC2_HOST }}:3001/api
        push: true
        tags: |
          ${{ steps.login-ecr.outputs.registry }}/zeetafin-frontend:${{ steps.set-tag.outputs.tag }}
          ${{ steps.login-ecr.outputs.registry }}/zeetafin-frontend:latest
        cache-from: type=gha
        cache-to: type=gha,mode=max

11. Verification Checklist & Challenge

  1. Workflow File Active

    .github/workflows/deploy.yml is committed to the main branch.

  2. Successful CI Run

    The build-and-push job finishes green in the GitHub Actions console.

  3. Dual Tags Verified in ECR

    Both zeetafin-backend and zeetafin-frontend display the current commit SHA and latest tags.

  4. Challenge Exercise

    Trigger a manual build via workflow_dispatch in GitHub Actions UI with tag_override: v1.0.0-release. Check ECR to confirm that this explicit tag was published.
