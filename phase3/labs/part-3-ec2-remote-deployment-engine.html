Lab Focus

Achieving atomic, repeatable, zero-collision container replacements on EC2 while protecting database persistence and operating within compute resource limits.

1. The Container Replacement Challenge

Deploying a new container version sounds simple: download the image and start it. However, in automated continuous deployment on a single EC2 host, naive deployments cause immediate failure.

Consider what happens if you run docker run -d -p 3000:3000 zeetafin-frontend:new while the old container is still running:

Failure Mode Root Cause Consequence
Port Conflict Port 3000 is already bound by the previous container. Error response from daemon: driver failed programming external connectivity: Bind for 0.0.0.0:3000 failed: port is already allocated
Name Collision Container name zeetafin-frontend already exists. Conflict. The container name "/zeetafin-frontend" is already in use by container "...". You have to remove (or rename) that container.
Downtime Window If you stop the container *before* pulling the image, pulling takes 45 seconds over the network. Users experience HTTP 502/504 downtime for almost a full minute during every deployment!

To satisfy the project requirement—"Ensure the old application container is replaced when a new version is deployed"—we architected a declarative deployment engine powered by Docker Compose native reconciliation.

2. Architecture of the Deployment Engine

Our solution decouples image transmission from container recreation:

  1. Background Image Download:

    docker compose -f docker-compose.prod.yml pull downloads the new layers from Amazon ECR in the background while the currently active containers continue serving incoming traffic.

  2. Atomic Recreation:

    docker compose -f docker-compose.prod.yml up -d --remove-orphans --force-recreate recreates the containers, atomically swapping the network namespace and port mapping in under 200 milliseconds.

  3. Persistent Storage Isolation:

    The database data volume (zeetafin_prod_pgdata) is defined as an external, named persistent volume. Recreating the database container leaves the disk blocks untouched.

  4. Automated Validation:

    healthcheck.sh probes http://127.0.0.1:3001/api/docs and http://127.0.0.1:3000/ in a retry loop. If both respond with HTTP 200, the deployment exits with code 0.

5. The Idempotent deploy.sh Engine

The core execution script phase3/scripts/deploy.sh is executed directly by GitHub Actions over SSH. It accepts the target Git SHA tag, authenticates against ECR, triggers container recreation, runs the healthcheck verification loop, and prunes old images:

Key Rollout Block in deploy.sh BASH 
# 1. Authenticate Docker with Amazon ECR on the EC2 host
aws ecr get-login-password --region "${AWS_REGION}" |   docker login --username AWS --password-stdin "${ECR_REGISTRY}"

# 2. Pull updated images in background
docker compose -f "${COMPOSE_FILE}" pull

# 3. Atomically replace old containers
docker compose -f "${COMPOSE_FILE}" up -d --remove-orphans --force-recreate

# 4. Probe endpoints until healthy
check_endpoint "http://127.0.0.1:3001/api/docs" "ZeetaFin Backend"
check_endpoint "http://127.0.0.1:3000/" "ZeetaFin Frontend"

# 5. Prune dangling layers
docker image prune -f --filter "until=24h" || true

6. Zero-Collision Mechanics Explained

Why does up -d --force-recreate --remove-orphans succeed where manual scripts fail?

Manual Bash Scripts (Fragile)

  1. docker stop old-container (Site goes down immediately)
  2. docker pull new-image (Takes 30+ seconds over internet)
  3. docker rm old-container
  4. docker run ...
Severe downtime & crash if pull fails

Docker Compose Engine (Production)

  1. Images pulled *before* any service is touched
  2. If pull fails, active containers are completely undisturbed!
  3. Once layers are cached locally, containers are swapped in milliseconds
Fault-tolerant, atomic & zero port collisions

7. SSH Remote Execution Step in GitHub Actions

In .github/workflows/deploy.yml, the deploy-to-ec2 job uses the standard OpenSSH agent to connect securely without third-party dependencies:

deploy-to-ec2 Execution Step YAML 
- name: Execute Deployment & Container Replacement on EC2
  env:
    EC2_USER: ${{ secrets.EC2_USERNAME || 'ubuntu' }}
    EC2_HOST: ${{ secrets.EC2_HOST }}
    ECR_REGISTRY: ${{ needs.build-and-push.outputs.ecr_registry }}
    IMAGE_TAG: ${{ needs.build-and-push.outputs.image_tag }}
  run: |
    ssh -i ~/.ssh/deploy_key -o StrictHostKeyChecking=no "${EC2_USER}@${EC2_HOST}" << 'EOF'
      set -euo pipefail
      cd /home/ubuntu/zeetafin-app
      chmod +x scripts/deploy.sh scripts/healthcheck.sh
      ./scripts/deploy.sh "${{IMAGE_TAG}}" "${{ECR_REGISTRY}}" "us-east-1"
    EOF

9. Disk Space Hygiene on t3.micro Instances

The Phase 1 EC2 instance runs with a 20 GiB gp3 root EBS volume. With regular CI/CD deployments pushing multiple 300 MB images each day, unpruned Docker caches would exhaust disk space within weeks (leading to No space left on device).

Our deploy.sh script automatically executes:

Prune Command BASH 
docker image prune -f --filter "until=24h"

This safely removes older unreferenced layers without discarding images needed for fast instant rollbacks.

10. Rapid Rollback Runbook

What if a faulty commit introduces a bug that slipped past staging? Because our images are tagged with Git SHAs in Amazon ECR, rolling back takes a single command on EC2 or via workflow_dispatch:

Instant Rollback Command on EC2 BASH 
$ cd /home/ubuntu/zeetafin-app
$ # Re-deploy the known-good Git commit SHA
$ ./scripts/deploy.sh 5eb7a625a... "${ECR_REGISTRY}" us-east-1

11. Verification Checklist & Challenge

  1. Deploy Manifests Synced

    docker-compose.prod.yml, deploy.sh, and healthcheck.sh reside in /home/ubuntu/zeetafin-app/.

  2. Clean Container Replacement Verified

    Executing deploy.sh replaces running containers without downtime or port is already allocated errors.

  3. Database Data Preserved

    Volume zeetafin_prod_pgdata retains all PostgreSQL tables across container recreations.

  4. Challenge Exercise

    Run docker ps on EC2, note the container IDs. Run ./scripts/deploy.sh again. Confirm that new container IDs are launched and the old ones are gracefully decommissioned.
