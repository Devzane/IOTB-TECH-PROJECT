1. Overview & Architecture

An automated CI/CD pipeline is only as secure as the credentials executing it. In Phase 3, GitHub Actions operates as an autonomous agent that must authenticate with AWS to push container images and connect over SSH to deploy onto our EC2 host.

Before writing a single line of GitHub Actions workflow YAML, we must configure three essential security boundaries:

1. Dedicated IAM Bot User

A programmatic non-human entity (zeetafin-ci-cd-bot) restricted strictly to Amazon ECR authorization, repository discovery, and image uploads.

2. Encrypted ECR Repositories

Server-side encrypted (KMS/AES-256) container registries with automated image vulnerability scanning and immutable layer storage.

3. GitHub Encrypted Secrets

Zero-exposure credential vault within the GitHub repository, preventing access keys and SSH private keys from leaking into version control.

2. CI/CD Credential Threat Modeling

Why can't we simply use our personal AWS Administrator credentials in GitHub Secrets? In enterprise DevOps, shared administrative credentials violate basic compliance and expose organizations to catastrophic blast radiuses:

Vector Administrative Credentials (Dangerous) Scoped Least-Privilege IAM (Production)
Compromise Impact Total AWS account takeover, data deletion, crypto-mining. Attacker can only write images to zeetafin-* ECR repos.
Audit & Attribution CloudTrail events indistinguishable from operator actions. Every push is strictly tagged to zeetafin-ci-cd-bot.
Revocation Velocity Revoking disrupts human engineers and admin consoles. Single-click deactivation without affecting engineers.
Never Commit Secrets to Version Control

Git history is immutable. Committing .pem keys, AWS credentials, or .env files to GitHub—even for a few seconds before deleting them—exposes them to automated scrapers. Always verify .gitignore before staging.

3. Least-Privilege IAM Policy

AWS provides the managed policy AmazonEC2ContainerRegistryPowerUser, which grants permissions to read, write, and list ECR repositories, but forbids deleting repositories. For higher security environments, we can scope this even further to our specific project ARN prefix:

zeetafin-ecr-least-privilege-policy.json JSON 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ECRAuthToken",
      "Effect": "Allow",
      "Action": [
        "ecr:GetAuthorizationToken"
      ],
      "Resource": "*"
    },
    {
      "Sid": "ManageZeetaFinRepositories",
      "Effect": "Allow",
      "Action": [
        "ecr:BatchCheckLayerAvailability",
        "ecr:GetDownloadUrlForLayer",
        "ecr:BatchGetImage",
        "ecr:PutImage",
        "ecr:InitiateLayerUpload",
        "ecr:UploadLayerPart",
        "ecr:CompleteLayerUpload",
        "ecr:DescribeRepositories",
        "ecr:ListImages",
        "ecr:DescribeImages"
      ],
      "Resource": "arn:aws:ecr:us-east-1:*:repository/zeetafin-*"
    }
  ]
}

4. Creating the IAM Bot User

We create the dedicated IAM user zeetafin-ci-cd-bot and attach the ECR PowerUser policy using the AWS CLI or AWS Management Console:

Terminal (Local Operator Machine) BASH 
$ # 1. Create the IAM user
$ aws iam create-user --user-name zeetafin-ci-cd-bot

$ # 2. Attach ECR PowerUser policy
$ aws iam attach-user-policy     --user-name zeetafin-ci-cd-bot     --policy-arn arn:aws:iam::aws:policy/AmazonEC2ContainerRegistryPowerUser

$ # 3. Generate Programmatic Access Key pair
$ aws iam create-access-key --user-name zeetafin-ci-cd-bot

The CLI outputs the Access Key credentials. Save these temporarily in a secure buffer—we will paste them directly into GitHub Secrets:

Output — create-access-key JSON 
{
    "AccessKey": {
        "UserName": "zeetafin-ci-cd-bot",
        "AccessKeyId": "AKIAIOSFODNN7EXAMPLE",
        "Status": "Active",
        "SecretAccessKey": "wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY",
        "CreateDate": "2026-10-19T13:45:00Z"
    }
}

5. Provisioning Amazon ECR Repositories

Our Phase 2 application consists of two decoupled services: the NestJS backend and Next.js frontend. We provision two discrete ECR repositories with KMS encryption and scan-on-push enabled:

Terminal (AWS CLI) BASH 
$ # Create zeetafin-backend repository
$ aws ecr create-repository     --repository-name zeetafin-backend     --image-tag-mutability MUTABLE     --image-scanning-configuration scanOnPush=true     --encryption-configuration encryptionType=AES256     --region us-east-1

$ # Create zeetafin-frontend repository
$ aws ecr create-repository     --repository-name zeetafin-frontend     --image-tag-mutability MUTABLE     --image-scanning-configuration scanOnPush=true     --encryption-configuration encryptionType=AES256     --region us-east-1

6. Vulnerability Scanning & CVE Auditing

By enabling scanOnPush=true, Amazon ECR automatically scans container layers against the Common Vulnerabilities and Exposures (CVE) database upon receipt. When images land in ECR, you can query their security health immediately:

Terminal (AWS CLI) BASH 
$ aws ecr describe-image-scan-findings     --repository-name zeetafin-backend     --image-id imageTag=latest     --region us-east-1

7. ECR Lifecycle Policies: Automated Pruning

Every CI/CD push generates new image tags. Without a lifecycle policy, untagged and historical layers accumulate, driving up AWS storage billing. We apply a policy to retain only the last 10 tagged builds and purge untagged intermediate layers after 7 days:

ecr-lifecycle-policy.json JSON 
{
  "rules": [
    {
      "rulePriority": 1,
      "description": "Expire untagged images older than 7 days",
      "selection": {
        "tagStatus": "untagged",
        "countType": "sinceImagePushed",
        "countUnit": "days",
        "countNumber": 7
      },
      "action": {
        "type": "expire"
      }
    },
    {
      "rulePriority": 2,
      "description": "Retain only the 10 most recent tagged releases",
      "selection": {
        "tagStatus": "any",
        "countType": "imageCountMoreThan",
        "countNumber": 10
      },
      "action": {
        "type": "expire"
      }
    }
  ]
}
Terminal (AWS CLI) BASH 
$ aws ecr put-lifecycle-policy     --repository-name zeetafin-backend     --lifecycle-policy-text file://ecr-lifecycle-policy.json

$ aws ecr put-lifecycle-policy     --repository-name zeetafin-frontend     --lifecycle-policy-text file://ecr-lifecycle-policy.json

8. Configuring GitHub Repository Secrets

Navigate to your repository on GitHub: Settings > Secrets and variables > Actions > New repository secret. Configure each of the following 6 secrets:

Secret Name Value / Origin Purpose
AWS_ACCESS_KEY_ID AKIA... from IAM user creation Authenticates GitHub Actions runner to AWS.
AWS_SECRET_ACCESS_KEY Secret key string from IAM creation AWS cryptographic signature key.
AWS_REGION us-east-1 Target AWS Region for ECR and EC2.
EC2_HOST Public IP from Phase 1 Terraform (e.g. 54.210.xx.xx) Destination host for SSH deployment connection.
EC2_USERNAME ubuntu Default SSH system user for Ubuntu 24.04 LTS.
EC2_SSH_KEY Complete contents of phase1-key.pem OpenSSH RSA Private key used to authenticate SSH session.
Formatting the EC2_SSH_KEY Secret

Ensure the entire PEM content is pasted, including the opening line -----BEGIN RSA PRIVATE KEY----- and ending line -----END RSA PRIVATE KEY-----, without adding extra blank lines or spaces.

9. Verifying ECR Auth & Registry Reachability

Before launching GitHub Actions, test the credentials locally to verify that the IAM user possesses valid permissions to retrieve an ECR authorization token and log in to Docker:

Terminal (Verification Command) BASH 
$ AWS_ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text)
$ echo "AWS Account: ${AWS_ACCOUNT_ID}"

$ # Authenticate Docker client against Amazon ECR registry
$ aws ecr get-login-password --region us-east-1 |     docker login --username AWS --password-stdin "${AWS_ACCOUNT_ID}.dkr.ecr.us-east-1.amazonaws.com"

Expected successful output:

Output SUCCESS 
WARNING! Your password will be stored unencrypted in /home/ubuntu/.docker/config.json.
Configure a credential helper to remove this warning. See
https://docs.docker.com/engine/reference/commandline/login/#credentials-store

Login Succeeded

10. Verification Checklist & Challenge

  1. IAM Bot User Configured

    User zeetafin-ci-cd-bot exists and has programmatic access keys generated.

  2. ECR Repositories Created

    Both zeetafin-backend and zeetafin-frontend are active in us-east-1 with AES-256 encryption.

  3. GitHub Secrets Injected

    All 6 required secrets (AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY, AWS_REGION, EC2_HOST, EC2_USERNAME, EC2_SSH_KEY) are saved.

  4. Challenge Exercise

    Run aws ecr describe-repositories --query "repositories[].repositoryUri" and verify that both URIs follow the standard <account-id>.dkr.ecr.us-east-1.amazonaws.com/<name> syntax.
