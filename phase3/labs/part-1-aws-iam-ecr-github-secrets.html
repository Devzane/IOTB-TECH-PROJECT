1. Overview & The CI/CD Mental Model

An automated CI/CD pipeline is only as secure and functional as the credentials executing it. Before GitHub Actions can build or deploy a single container, it must have clear, pre-authorized security boundaries in both AWS and GitHub.

Why Must This Be Done First?

A workflow file (like .github/workflows/deploy.yml) is merely a set of instructions written in text. When GitHub Actions triggers, it runs on an isolated server in GitHub's cloud. That server knows nothing about your AWS account. If you push a workflow YAML file before creating your IAM bot user and injecting your GitHub Secrets, the very first step will crash with: Credentials could not be loaded or Access Denied.

To establish zero-trust automated deployment, we configure three essential security pillars:

1. Dedicated IAM Bot User

A non-human identity (zeetafin-ci-cd-bot) with programmatic access keys, restricted strictly to ECR authentication and image uploads.

2. Encrypted ECR Repositories

Private container registries (zeetafin-backend & zeetafin-frontend) encrypted with AES-256 and configured with automated vulnerability scanning.

3. GitHub Encrypted Secrets

A secure cryptographic vault inside GitHub repository settings storing your AWS keys and EC2 SSH private key without exposing them in Git code.

3. CI/CD Credential Threat Modeling

Why can't we simply use our personal AWS Administrator credentials in GitHub Secrets? In professional engineering, shared administrative credentials violate compliance and expose organizations to catastrophic risks:

Threat Vector Administrator Keys (Dangerous) Scoped Least-Privilege Bot (Production Standard)
Secret Leak in Logs Total account takeover: attacker can spin up $10,000/day crypto-miners or delete all databases. Attacker can only upload container images to designated zeetafin-* registries.
Audit & Compliance CloudTrail logs cannot distinguish between human developers and automated robot actions. Every single build and image push is auditable and attributed to zeetafin-ci-cd-bot.
Revocation Velocity Revoking the key disrupts human engineers, locked admin portals, and local dev environments. Single-click deactivation in IAM immediately stops the rogue runner without touching human access.

4. Step-by-Step: Creating the IAM Bot User

You can execute this task using either the AWS Web Console (recommended for beginners) or the AWS CLI (for terminal pros). Choose whichever method you prefer:

Method A

Using AWS Web Management Console (Visual Walkthrough)

  1. Log in to AWS Console & Navigate to IAM

    Open your browser and navigate to https://console.aws.amazon.com/. In the top search bar (or press Alt + S), type IAM and click on IAM (Identity and Access Management).

  2. Open the Users Page

    In the left-hand navigation menu under Access management, click Users.

  3. Initiate User Creation

    In the top-right corner, click the bright orange button labeled Create user.

  4. Configure User Details (Step 1 of 3)

    In the User name field, enter: zeetafin-ci-cd-bot.

    CRITICAL: Leave the checkbox "Provide user access to the AWS Management Console" UNCHECKED. (This is a programmatic robot that only runs via code; it does not need a web console login password).

    Click the orange Next button at the bottom-right.

  5. Attach Permissions Directly (Step 2 of 3)

    Under Permissions options, click the radio button for Attach policies directly.

    In the Filter policies search bar, type: AmazonEC2ContainerRegistryPowerUser.

    Check the checkbox next to AmazonEC2ContainerRegistryPowerUser.

    What does PowerUser grant?

    It allows the bot to read, write, and push container images to ECR, but explicitly forbids it from deleting entire repositories or modifying IAM roles.

    Click the orange Next button.

  6. Review and Create

    Review the details: User name = zeetafin-ci-cd-bot, Policy = AmazonEC2ContainerRegistryPowerUser. Click Create user.

  7. Open Security Credentials & Create Access Key

    You are returned to the Users list. Click on the newly created user name zeetafin-ci-cd-bot.

    Select the Security credentials tab (located next to Permissions and Tags).

    Scroll down to the Access keys card and click the button labeled Create access key.

  8. Select Use Case

    Under Access key best practices & alternatives, select the radio button: Command Line Interface (CLI) (or Application running outside AWS).

    Scroll to the bottom, check the confirmation checkbox: "I understand the above recommendation and want to proceed to create an access key." Click Next.

    (Optional) Tag description: type GitHub Actions CI/CD Runner. Click Create access key.

  9. Save Credentials (CRITICAL LIFETIME STEP)

    You will see a success screen with two values:

    • Access key: A 20-character identifier starting with AKIA... (e.g. AKIA...[16 random letters/digits]).
    • Secret access key: Click the Show link to reveal the 40-character secret key.
    Save These Keys Immediately!

    AWS will NEVER show you this Secret Access Key again after you leave this page. Click Download .csv file or copy both keys into a secure temporary text note. We will paste them directly into GitHub Secrets in Section 7.

    Click Done.

Method B

Using AWS CLI (Terminal Commands)

If you prefer running commands directly from your local terminal (PowerShell, Bash, or Zsh), execute these three commands sequentially:

Terminal (AWS CLI Execution) BASH / POWERSHELL 
# Step 1: Create the dedicated non-human bot user
$ aws iam create-user --user-name zeetafin-ci-cd-bot

# Step 2: Attach the standard ECR PowerUser managed policy
$ aws iam attach-user-policy \
    --user-name zeetafin-ci-cd-bot \
    --policy-arn arn:aws:iam::aws:policy/AmazonEC2ContainerRegistryPowerUser

# Step 3: Generate programmatic access keys for the bot
$ aws iam create-access-key --user-name zeetafin-ci-cd-bot

5. Step-by-Step: Provisioning Amazon ECR Repositories

Our ZeetaFin platform consists of two decoupled application tiers: the NestJS backend and Next.js frontend. Each tier requires its own dedicated Amazon ECR private repository.

Method A

Creating Repositories via AWS Web Console

  1. Navigate to Amazon ECR

    In the AWS Console top search bar, type ECR and select Elastic Container Registry.

    Verify that your region in the top-right corner is set to us-east-1 (N. Virginia).

  2. Open Repositories

    In the left sidebar menu, expand Amazon ECR → Private registry and click Repositories.

  3. Create Backend Repository

    Click the orange Create repository button.

    • Visibility settings: Select Private.
    • Repository name: Type zeetafin-backend.
    • Tag mutability: Select Mutable (allows updating tags like latest).
    • Scan on push: Toggle the switch to Enabled (automatically scans images for security vulnerabilities).
    • Encryption settings: Select AES-256 (standard zero-cost server-side encryption).

    Click the orange Create repository button at the bottom.

  4. Create Frontend Repository

    Click Create repository again and repeat with the exact same settings for the frontend:

    • Visibility settings: Private
    • Repository name: Type zeetafin-frontend
    • Tag mutability: Mutable | Scan on push: Enabled | Encryption: AES-256

    Click Create repository.

  5. Verify Both Repositories

    You should now see both zeetafin-backend and zeetafin-frontend listed in the table. Note their URI format: <account-id>.dkr.ecr.us-east-1.amazonaws.com/<name>.

Method B

Creating Repositories via AWS CLI

Terminal (AWS CLI Creation) BASH / POWERSHELL 
# Create zeetafin-backend repository
$ aws ecr create-repository \
    --repository-name zeetafin-backend \
    --image-tag-mutability MUTABLE \
    --image-scanning-configuration scanOnPush=true \
    --encryption-configuration encryptionType=AES256 \
    --region us-east-1

# Create zeetafin-frontend repository
$ aws ecr create-repository \
    --repository-name zeetafin-frontend \
    --image-tag-mutability MUTABLE \
    --image-scanning-configuration scanOnPush=true \
    --encryption-configuration encryptionType=AES256 \
    --region us-east-1

6. ECR Lifecycle Policies: Automated Pruning

Every commit pushed to GitHub will trigger an automated build that generates a new container image in ECR. Over time, accumulating gigabytes of historical images drives up AWS storage costs. We apply an automated lifecycle policy that expires untagged builds after 7 days and retains only the 10 most recent tagged releases:

ecr-lifecycle-policy.json JSON 
{
  "rules": [
    {
      "rulePriority": 1,
      "description": "Expire untagged images older than 7 days",
      "selection": {
        "tagStatus": "untagged",
        "countType": "sinceImagePushed",
        "countUnit": "days",
        "countNumber": 7
      },
      "action": {
        "type": "expire"
      }
    },
    {
      "rulePriority": 2,
      "description": "Retain only the 10 most recent tagged releases",
      "selection": {
        "tagStatus": "any",
        "countType": "imageCountMoreThan",
        "countNumber": 10
      },
      "action": {
        "type": "expire"
      }
    }
  ]
}

Apply this policy to both repositories via CLI:

Terminal (Apply Lifecycle Policy) BASH 
$ aws ecr put-lifecycle-policy \
    --repository-name zeetafin-backend \
    --lifecycle-policy-text file://ecr-lifecycle-policy.json

$ aws ecr put-lifecycle-policy \
    --repository-name zeetafin-frontend \
    --lifecycle-policy-text file://ecr-lifecycle-policy.json

7. Step-by-Step: Configuring GitHub Repository Secrets

GitHub Encrypted Secrets act as a digital vault. They allow your automated workflow YAML scripts to authenticate against AWS and connect to your EC2 server without ever checking sensitive passwords or private keys into Git.

How to Access the GitHub Secrets Manager

  1. Open Your Repository in GitHub

    Open your browser and navigate to your project repository: https://github.com/<your-username>/<your-repo-name> (for example, https://github.com/Devzane/IOTB-TECH-PROJECTS).

  2. Open Repository Settings

    Look at the horizontal tab bar underneath the repository title (Code, Issues, Pull requests, Actions, Projects, Wiki, Security, Insights, Settings). Click on the gear icon labeled Settings on the far right.

  3. Navigate to Secrets & Variables → Actions

    In the left-hand navigation sidebar, scroll down to the Security section. Click on Secrets and variables to expand it, then click on Actions.

  4. Click "New repository secret"

    On the right side of the page under the Repository secrets heading, click the green button labeled New repository secret.

The 6 Required Secrets: Where to Find & How to Enter Each One

You must add each of the following 6 secrets one by one. For each secret, click New repository secret, type the exact Name (in ALL CAPS), paste the exact Secret value, and click Add secret.

AWS_ACCESS_KEY_ID AWS Authentication

The programmatic identification key generated for the zeetafin-ci-cd-bot IAM user.

Where to get it: From Section 4 when you created the access key (or from the downloaded .csv file). It is a 20-character string beginning with AKIA....
AWS_SECRET_ACCESS_KEY AWS Cryptographic Signature

The confidential signature key corresponding to the bot user's access key.

Where to get it: From Section 4 when you clicked "Show Secret Access Key" (or column 2 in your downloaded .csv file). It is a ~40-character alphanumeric string.
AWS_REGION Deployment Target

The target AWS data center region where your ECR repositories and EC2 server exist.

Where to get it: Type literally: us-east-1 (all lowercase, no spaces).
EC2_HOST Network Destination

The public IPv4 address of your Phase 1 AWS EC2 instance.

Where to get it:
  • Method A (AWS Console): Open AWS Console → Search EC2 → Click Instances → Click your running instance → In the Details tab at the bottom, find Public IPv4 address (e.g., 54.210.123.45) and click the copy icon.
  • Method B (CLI): Run aws ec2 describe-instances --filters "Name=instance-state-name,Values=running" --query "Reservations[].Instances[].PublicIpAddress" --output text
⚠️ Notice: Paste ONLY the raw IP address (e.g., 54.210.123.45). Do NOT include http:// or port numbers like :3000!
EC2_USERNAME SSH User

The operating system SSH user configured on your Ubuntu 24.04 LTS instance.

Where to get it: Type literally: ubuntu (all lowercase).
EC2_SSH_KEY SSH Private Key

The complete OpenSSH private key used to authenticate an encrypted terminal session into your EC2 host.

Where to get it:

This is the private key file you created in Phase 1 (typically named phase1-key.pem or stored at ~/.ssh/phase1-key).

How to open and copy it:

  • On Windows (PowerShell): Run Get-Content ~/.ssh/phase1-key or open the file in VS Code / Notepad.
  • On macOS / Linux: Run cat ~/.ssh/phase1-key.
Must Include Header & Footer Lines!

You must copy the ENTIRE file content, including the very first line -----BEGIN RSA PRIVATE KEY----- (or BEGIN OPENSSH PRIVATE KEY), all the base64 encrypted lines in between, and the very last line -----END RSA PRIVATE KEY-----. Do NOT add trailing spaces.

8. Local Pre-Flight Verification

Before relying on GitHub Actions, verify that both your AWS ECR authentication and SSH reachability work from your local machine. If these two tests pass locally, your CI/CD pipeline is guaranteed to authenticate cleanly.

Test 1: Docker Login to Amazon ECR

Run the login pipe command in your terminal. Docker will request a temporary authorization token through the AWS CLI and log in:

Terminal (ECR Authentication Test) BASH / POWERSHELL 
# Resolve your AWS Account ID automatically
$ AWS_ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text)
$ echo "AWS Account: ${AWS_ACCOUNT_ID}"

# Execute Docker login to your private ECR registry
$ aws ecr get-login-password --region us-east-1 | \
    docker login --username AWS --password-stdin "${AWS_ACCOUNT_ID}.dkr.ecr.us-east-1.amazonaws.com"

Expected successful output:

Output SUCCESS 
WARNING! Your password will be stored unencrypted in /home/ubuntu/.docker/config.json.
Login Succeeded

Test 2: EC2 SSH Remote Command Execution

Verify that your SSH private key can establish an automated non-interactive terminal session to your EC2 instance:

Terminal (SSH Connectivity Test) BASH / POWERSHELL 
$ ssh -i ~/.ssh/phase1-key -o StrictHostKeyChecking=no ubuntu@<YOUR_EC2_PUBLIC_IP> "docker --version && docker compose version"

Expected output: Displays the installed Docker and Docker Compose versions without prompting for a password.

9. Beginner Troubleshooting: Common Mistakes & Fixes

Symptom / Error Message Root Cause Exact Step-by-Step Fix
Credentials could not be loaded in GitHub Actions AWS_ACCESS_KEY_ID or AWS_SECRET_ACCESS_KEY missing, misspelled, or has trailing spaces. Go to GitHub → Settings → Secrets and variables → Actions. Verify the secret names are in ALL CAPS. Click the pencil icon to re-paste the exact key without spaces.
AccessDeniedException: User ... is not authorized during ECR push The IAM user lacks the AmazonEC2ContainerRegistryPowerUser policy. Open AWS Console → IAM → Users → zeetafin-ci-cd-bot → Permissions → Click Add permissions → Attach AmazonEC2ContainerRegistryPowerUser.
ssh: connect to host ... port 22: Connection timed out The EC2 Security Group inbound rule does not permit SSH traffic on port 22. Open AWS Console → EC2 → Security Groups → Edit inbound rules → Add rule: Type: SSH (Port 22), Source: 0.0.0.0/0 (or your runner IP range). Save rules.
Load key "...": error in libcrypto / invalid format The EC2_SSH_KEY secret was pasted without the -----BEGIN... or -----END... headers. Re-open your phase1-key.pem file in Notepad/VS Code, press Ctrl + A to select everything, copy, and re-save into GitHub Secrets.
Cannot perform an interactive login on a non TTY Missing the pipe | or --password-stdin in the Docker login command. Ensure the login command uses aws ecr get-login-password | docker login --username AWS --password-stdin ....

10. Verification Checklist & Challenge

  1. IAM Bot User Active

    User zeetafin-ci-cd-bot exists in IAM, has AmazonEC2ContainerRegistryPowerUser attached, and has active programmatic keys.

  2. ECR Repositories Provisioned

    Both zeetafin-backend and zeetafin-frontend are active in us-east-1 with AES-256 encryption and Scan on push enabled.

  3. Lifecycle Policies Attached

    Both repositories have automated pruning rules expiring untagged layers older than 7 days.

  4. All 6 GitHub Secrets Stored

    Verify under Settings → Secrets and variables → Actions that all 6 secrets exist: AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY, AWS_REGION, EC2_HOST, EC2_USERNAME, EC2_SSH_KEY.

  5. Hands-on Challenge

    Run aws ecr describe-repositories --query "repositories[].repositoryUri" and verify that both URIs follow the standard <account-id>.dkr.ecr.us-east-1.amazonaws.com/<name> syntax.
