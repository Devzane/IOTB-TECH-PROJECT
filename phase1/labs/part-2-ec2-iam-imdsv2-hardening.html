1. The Nitro Compute Plane: Why t3.micro?

Choosing an EC2 instance type requires understanding hypervisor architectures, CPU bursting credits, and cost optimization. In Phase 1, we select t3.micro running on AWS Nitro.

The AWS Nitro System offloads storage (NVMe), networking (ENA), and hypervisor management to dedicated Nitro PCIe cards. Unlike legacy Xen hypervisors (like the older t2 generation), almost 100% of host CPU and memory are dedicated to your virtual machine.

2. Dynamic AMI Resolution with aws_ami

A classic beginner mistake is hardcoding an Amazon Machine Image ID:

Anti-pattern — Do NOT do thisANTI-PATTERN
# Fragile: This AMI ID only exists in us-east-1 and will be deprecated by Canonical in months
ami = "ami-0c7217cdde317cfec"

In Phase 1, we use an automated aws_ami data source that dynamically queries Canonical's official AWS account:

phase1/main.tf — aws_ami data source TERRAFORM 
data "aws_ami" "ubuntu" {
  most_recent = true
  owners      = ["099720109477"] # Canonical's official, verified AWS Account ID

  filter {
    name   = "name"
    values = ["ubuntu/images/hvm-ssd-gp3/ubuntu-noble-24.04-amd64-server-*"]
  }

  filter {
    name   = "virtualization-type"
    values = ["hvm"]
  }

  filter {
    name   = "architecture"
    values = ["x86_64"]
  }
}
Why This is Enterprise Standard

1. Region portability: You can change region = "eu-west-1" and Terraform will resolve the correct regional AMI ID with zero code edits.
2. Security patches: Whenever Canonical publishes a refreshed Ubuntu 24.04 release image with kernel and security patches, a future terraform plan will alert you to the update.
3. Supply chain integrity: Filtering strictly by owners = ["099720109477"] guarantees you never accidentally boot a malicious community AMI containing backdoors.

3. The IMDSv1 vs IMDSv2 Security Revolution

The Instance Metadata Service (IMDS) runs at link-local address 169.254.169.254. It allows code on an EC2 instance to learn its own IP, instance ID, and fetch temporary AWS STS credentials from attached IAM roles.

In 2019, the Capital One breach exposed over 100 million customer records. The attacker exploited a Server-Side Request Forgery (SSRF) vulnerability in an open-source web application. The application was tricked into making an HTTP GET request to http://169.254.169.254/latest/meta-data/iam/security-credentials/, dumping the instance's AWS secret access keys directly to the attacker.

IMDSv1 Vulnerability Path

Uses simple HTTP GET requests with no session tokens. Any SSRF bug or misconfigured proxy can steal credentials instantly.

GET http://169.254.169.254/latest/meta-data/iam/security-credentials/ ──► 200 OK (Leaks AccessKeyId & SecretAccessKey!)

IMDSv2 Defense in Depth

Session-oriented. Requires a PUT request with a mandatory TTL header to generate a cryptographically signed token first.

GET http://169.254.169.254/latest/meta-data/ ──► 401 Unauthorized (SSRF Attempt Neutralized!)

Here is how we enforce IMDSv2 in phase1/main.tf:

phase1/main.tf — metadata_options TERRAFORM 
  metadata_options {
    http_endpoint               = "enabled"
    http_tokens                 = "required" # Disables IMDSv1 completely
    http_put_response_hop_limit = 1          # Prevents container/proxy SSRF packet relay
  }
The Critical Role of http_put_response_hop_limit = 1

When an IP packet crosses a network bridge or Layer 3 boundary (such as Docker bridge networking docker0), its IP Time-To-Live (TTL / hop count) decrements by 1. Setting http_put_response_hop_limit = 1 means the response packet can ONLY reach processes running in the host network namespace. If an application inside a Docker container tries to generate an IMDSv2 token, the response TTL expires at the bridge and the packet is dropped!

4. Encrypted EBS gp3 Storage Engineering

Every server needs reliable, fast root storage. In Phase 1, we configure a 20 GiB General Purpose SSD (gp3) volume:

phase1/main.tf — root_block_device TERRAFORM 
  root_block_device {
    volume_type           = "gp3"
    volume_size           = 20
    encrypted             = true # KMS AES-256 encryption at rest
    delete_on_termination = true # Automatically clean up storage on terraform destroy
  }

Key architectural properties:

  • KMS Hardware Encryption: AWS Key Management Service encrypts data at rest, in-flight between EC2 and EBS, and in all snapshots created from the volume using AES-256. Because decryption happens on the dedicated Nitro card, there is zero CPU overhead on the Ubuntu OS.
  • gp3 Performance: Baseline performance is 3,000 IOPS and 125 MB/s, ensuring rapid Docker daemon startup, fast image layer untarring, and smooth apt upgrades.
  • delete_on_termination = true: Prevents "zombie EBS volumes" from being orphaned in your AWS account when you run terraform destroy, avoiding unnecessary billing charges.

5. IAM Least Privilege: The Zero-Permission Pattern

In Phase 1, the instance does not make any AWS API calls. So why did we create an IAM role and instance profile?

phase1/main.tf — IAM Resources TERRAFORM 
data "aws_iam_policy_document" "ec2_assume" {
  statement {
    effect  = "Allow"
    actions = ["sts:AssumeRole"]
    principals {
      type        = "Service"
      identifiers = ["ec2.amazonaws.com"]
    }
  }
}

resource "aws_iam_role" "ec2" {
  name               = "${var.project_name}-${var.environment}-ec2-role"
  assume_role_policy = data.aws_iam_policy_document.ec2_assume.json
  # Zero policies attached — least privilege baseline!
}

resource "aws_iam_instance_profile" "ec2" {
  name = "${var.project_name}-${var.environment}-ec2-profile"
  role = aws_iam_role.ec2.name
}

The Architectural Rationale:

If you launch an EC2 instance without an IAM instance profile, attaching one later via Terraform often causes instance replacement or complex lifecycle recreation depending on AWS API states. By establishing an empty, zero-permission role now:

  1. We adhere to least privilege: a compromised Phase 1 instance has zero permissions to touch S3, DynamoDB, or IAM.
  2. In Phase 2, when we need to pull private container images from Amazon ECR, we simply attach AmazonEC2ContainerRegistryReadOnly to this existing role. The instance gains ECR permissions dynamically with zero downtime and zero instance rebuilds!

6. Ed25519 Cryptographic SSH Key Management

Legacy systems still use 2048-bit or 4096-bit RSA keys. In Phase 1, we use Ed25519 (Edwards-curve Digital Signature Algorithm):

FeatureRSA 4096Ed25519 (Phase 1)
Security Strength~128 bits~128 bits
Public Key Length~736 characters (slow to transmit)68 characters (compact & clean)
Signature SpeedSlowerExtremely fast
Side-Channel ImmunityVulnerable to timing attacks if unblindedConstant-time by design

How Terraform ingests your public key:

phase1/main.tf — aws_key_pair TERRAFORM 
resource "aws_key_pair" "main" {
  key_name   = "${var.project_name}-${var.environment}-key"
  public_key = file(pathexpand(var.ssh_public_key_path))
}

Absolute Security Rule: file(pathexpand(...)) reads ONLY the .pub public key file from your local disk. Your private key (phase1-key) NEVER enters Terraform configuration, NEVER enters terraform.tfstate, and NEVER leaves your local machine.

8. Production Failures, Forensics, and Triage

Scenario 1: Testing and Proving IMDSv2 SSRF Immunity

Experiment & Verification

How do you prove to an enterprise security auditor that your instance is immune to classic IMDSv1 SSRF attacks?

View Verification Runbook & Output

Log into your EC2 server and attempt a raw GET request:

EC2 Bash — Raw GET Attempt
ubuntu@phase1-server:~$ curl -i http://169.254.169.254/latest/meta-data/
HTTP/1.1 401 Unauthorized
Content-Type: text/html
Date: Mon, 19 Oct 2026 12:00:00 GMT
Connection: close

<html><head><title>401 - Unauthorized</title></head><body>Unauthorized</body></html>

Now perform the legitimate IMDSv2 token flow:

EC2 Bash — IMDSv2 Two-Step Authentication
# Step 1: Request signed session token valid for 6 hours (21600 seconds)
ubuntu@phase1-server:~$ TOKEN=$(curl -s -X PUT "http://169.254.169.254/latest/api/token" \
    -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")

# Step 2: Query metadata with the token
ubuntu@phase1-server:~$ curl -s -H "X-aws-ec2-metadata-token: $TOKEN" http://169.254.169.254/latest/meta-data/instance-id
i-086381ab281249fa1

Because an SSRF attacker cannot force a server to issue custom PUT requests with arbitrary custom headers, the exploit path is completely blocked.

Scenario 2: The Unprotected Private Key Permission Error

Symptom

You try to connect to your instance with ssh -i ~/.ssh/phase1-key ubuntu@54.89.144.201, but OpenSSH aborts immediately with a scary error: WARNING: UNPROTECTED PRIVATE KEY FILE! Permissions 0644 for '/home/user/.ssh/phase1-key' are too open. It is required that your private key files are NOT accessible by others.

View Fix for Linux, macOS & Windows

OpenSSH enforces strict POSIX filesystem permissions. If group or world can read your private key, SSH refuses to use it.

On Linux / macOS:

Bash
$ chmod 600 ~/.ssh/phase1-key
$ chmod 644 ~/.ssh/phase1-key.pub

On Windows (PowerShell using icacls):

PowerShell
PS> icacls $HOME\.ssh\phase1-key /inheritance:r
PS> icacls $HOME\.ssh\phase1-key /grant:r "$($env:USERNAME):(R)"

Scenario 3: Unencrypted Snapshot Drift Detection

Symptom

A cloud engineer manually creates an unencrypted volume snapshot before maintenance. When the backup is restored, compliance audits fail because customer data is now sitting on an unencrypted volume.

View Remediation & Account-Level Enforcement

To prevent unencrypted volumes from ever being created in your AWS account, enable Account-Level EBS Encryption by Default:

AWS CLI
$ aws ec2 enable-ebs-encryption-by-default --region us-east-1
{
    "EbsEncryptionByDefault": true
}

Once enabled, any volume created in the region (whether via Terraform, CLI, or Console) will automatically be encrypted using AWS KMS.

10. Hands-on Muscle Memory Exercises

  1. Verify Live Volume Encryption

    SSH into the instance and run lsblk -f. Inspect the root device /dev/nvme0n1p1.

  2. Query Instance Metadata Options with AWS CLI

    Run aws ec2 describe-instances --instance-ids <instance_id> --query "Reservations[0].Instances[0].MetadataOptions". Confirm HttpTokens is required.

  3. Inspect IAM Instance Profile Association

    Run aws ec2 describe-iam-instance-profile-associations --filters "Name=instance-id,Values=<instance_id>". Verify the role matches phase1-dev-ec2-role.
