1. Why Custom VPCs Matter in Production

Every AWS account comes with a "Default VPC" in each region. In beginner tutorials, people deploy straight into the default VPC because it works immediately without extra code. In real production, launching into the default VPC is an immediate red flag.

A Virtual Private Cloud (VPC) is your logically isolated software-defined data center inside AWS. It defines your network boundaries, IP address pools, routing policies, and ingress/egress filtering rules.

Default AWS VPC

  1. Shared by default across all team members and unmanaged resources.
  2. Uses fixed 172.31.0.0/16 range — cannot peer with on-premises or other VPCs using the same CIDR.
  3. All subnets are automatically public with default routes to IGW.
  4. Default Security Group allows unrestricted intra-VPC communication.
High blast radius & security risk

Custom Dedicated VPC (Phase 1)

  1. Complete isolation for the ZeetaFin project.
  2. Custom non-overlapping CIDR: 10.0.0.0/16 tailored for multi-environment expansion.
  3. Explicit subnetting: public subnet for ingress, future private subnets for database.
  4. Explicit, least-privilege security groups locked strictly to operator /32.
Zero-trust perimeter & clean audit
DevOps Mental Model

A VPC is not just plumbing. It is the primary security boundary. If an attacker breaches an EC2 instance in a custom VPC, they can only reach resources routed within that specific VPC. They cannot see or pivot to databases or workloads running in other project VPCs.

2. CIDR & Subnet Math Explained

In Phase 1, we define two network ranges in variables.tf:

  • vpc_cidr = "10.0.0.0/16"
  • public_subnet_cidr = "10.0.1.0/24"

What do these numbers actually mean?

CIDR BlockPrefixTotal IP AddressesUsable in AWSPurpose
10.0.0.0/16/162(32-16) = 65,53665,531Entire VPC address pool
10.0.1.0/24/242(32-24) = 256251Public Subnet (DMZ / Operator Server)
10.0.2.0/24/24256251Reserved for Phase 2/3 Private App Subnet
10.0.3.0/24/24256251Reserved for Phase 2/3 Database Subnet
The 5 AWS Reserved IPs in Every Subnet

In standard IPv4 networking, only 2 addresses are reserved per subnet (Network ID and Broadcast). However, in every AWS subnet, exactly 5 IP addresses are reserved and cannot be assigned to instances:

  • 10.0.1.0: Network address
  • 10.0.1.1: Reserved by AWS for VPC router
  • 10.0.1.2: Reserved by AWS for DNS (AmazonProvidedDNS)
  • 10.0.1.3: Reserved by AWS for future use
  • 10.0.1.255: Network broadcast address (AWS does not support broadcast, but reserves it)

Therefore, a /24 provides 251 assignable IPs. The first instance launched in 10.0.1.0/24 will always receive private IP 10.0.1.4 or higher!

3. Declarative IaC vs Imperative Scripts

Why do we use Terraform instead of a Bash script with aws ec2 create-vpc?

Bash scripts are imperative: they tell the computer how to execute commands sequentially. If a script fails midway, you are left with half-provisioned resources. Re-running the script will fail because the VPC already exists, but the subnet does not.

Terraform is declarative: you declare the desired target state. Terraform compiles a Directed Acyclic Graph (DAG) of dependencies, compares your code against the real world recorded in terraform.tfstate, calculates the exact delta, and executes only what is needed.

Terraform State Engine Workflow CONCEPT 
[ .tf Configuration Code ]  ──( desired state )──┐
                                                  ▼
[ terraform.tfstate File ]  ──( recorded state )──► [ Terraform Plan Engine ] ──► [ Execution Delta ]
                                                  ▲                                (+ Create / ~ Change / - Destroy)
[ AWS Cloud API ]           ──( actual state )────┘

4. Line-by-Line Network Code Anatomy

Let's inspect the actual resources from phase1/main.tf that establish the network.

A. The Virtual Private Cloud (aws_vpc)

phase1/main.tf TERRAFORM 
resource "aws_vpc" "main" {
  cidr_block           = var.vpc_cidr
  enable_dns_support   = true # Enables AmazonProvidedDNS (10.0.0.2)
  enable_dns_hostnames = true # Assigns public DNS names to instances with public IPs

  tags = {
    Name = "${var.project_name}-${var.environment}-vpc"
  }
}
resource "aws_vpc" "main" { cidr_block = var.vpc_cidr enable_dns_hostnames = true }
Resource Type Local Identifier Argument Variable Reference

Critical Detail: enable_dns_hostnames = true is mandatory if you want EC2 instances to receive AWS public DNS hostnames (like ec2-x-x-x-x.compute-1.amazonaws.com). Without this, instances only receive raw public IP addresses.

B. The Internet Gateway (aws_internet_gateway)

phase1/main.tf TERRAFORM 
resource "aws_internet_gateway" "main" {
  vpc_id = aws_vpc.main.id

  tags = { Name = "${var.project_name}-${var.environment}-igw" }
}

An Internet Gateway is horizontally scaled, redundant, and highly available by design. It performs 1-to-1 NAT between an EC2 instance's private IP and its public IPv4 address, and routes outbound packets to the global internet.

C. The Public Subnet (aws_subnet)

phase1/main.tf TERRAFORM 
resource "aws_subnet" "public" {
  vpc_id                  = aws_vpc.main.id
  cidr_block              = var.public_subnet_cidr
  availability_zone       = var.availability_zone
  map_public_ip_on_launch = true # Auto-assigns public IP on boot

  tags = { Name = "${var.project_name}-${var.environment}-public-subnet" }
}

Setting map_public_ip_on_launch = true ensures that any EC2 instance launched into this subnet automatically gets a dynamic public IPv4 address from AWS's pool. This eliminates the requirement to purchase an Elastic IP (EIP), saving roughly $3.60/month.

D. Route Table & Association

phase1/main.tf TERRAFORM 
resource "aws_route_table" "public" {
  vpc_id = aws_vpc.main.id

  route {
    cidr_block = "0.0.0.0/0"
    gateway_id = aws_internet_gateway.main.id
  }

  tags = { Name = "${var.project_name}-${var.environment}-public-rt" }
}

resource "aws_route_table_association" "public" {
  subnet_id      = aws_subnet.public.id
  route_table_id = aws_route_table.public.id
}

A subnet is purely private until its Route Table contains a default route (0.0.0.0/0) pointing to an aws_internet_gateway, AND the subnet is explicitly associated with that route table via aws_route_table_association.

5. Defense-in-Depth: Security Group Architecture

Security Groups are the virtual firewalls operating at the hypervisor level on each network interface (ENI). They are stateful: if you send an outbound request, return traffic is automatically permitted regardless of inbound rules.

phase1/main.tf — aws_security_group TERRAFORM 
resource "aws_security_group" "ec2" {
  name        = "${var.project_name}-${var.environment}-ec2-sg"
  description = "SSH from my IP only. All egress allowed so apt and Docker can reach the internet."
  vpc_id      = aws_vpc.main.id

  # INGRESS: Strictly locked to a single /32 IP
  ingress {
    description = "SSH from operator IP"
    from_port   = 22
    to_port     = 22
    protocol    = "tcp"
    cidr_blocks = [var.my_ip] # e.g., "197.210.x.x/32"
  }

  # EGRESS: Permitted so apt update, Docker Hub pulls, and NTP work
  egress {
    description = "All outbound"
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }

  tags = { Name = "${var.project_name}-${var.environment}-ec2-sg" }
}
Why 0.0.0.0/0 Ingress on Port 22 is Unacceptable

Opening port 22 to 0.0.0.0/0 will result in your instance receiving automated SSH dictionary attacks from bots (Mirai, Shodan scanners, brute forcers) within 90 seconds of provisioning. Locking to var.my_ip (/32 CIDR) makes your server completely invisible to global internet port sweeps.

6. Variables, Outputs, and State Hygiene

A senior DevOps engineer separates variable definitions from real secrets and environment values:

Declares inputs with strict types, descriptions, and sensible defaults. Committed to Git.

7. The Professional Terraform CLI Lifecycle

Never run terraform apply blindly without formatting, validation, and a saved plan file:

  1. Format check: Ensure clean, idiomatic HCL style

    Run terraform fmt -check -recursive. In CI pipelines, this fails if any file is unformatted.

    Terminal
    $ terraform fmt -check -recursive
# Exit code 0 means all .tf files match HashiCorp canonical formatting
  2. Initialize working directory and provider plugins

    Downloads the AWS provider (~> 5.0) and local provider specified in versions.tf.

    Terminal
    $ terraform init
Terraform has been successfully initialized!
  3. Static validation without calling AWS APIs

    Checks HCL syntax, missing arguments, and type compatibility.

    Terminal
    $ terraform validate
Success! The configuration is valid.
  4. Generate and lock an explicit plan file

    Always output the plan to a binary file (-out=tfplan). This prevents race conditions where someone creates resources between plan and apply.

    Terminal
    $ terraform plan -out=tfplan
Plan: 11 to add, 0 to change, 0 to destroy.
  5. Apply the exact plan file

    Applying tfplan guarantees that only what was reviewed in step 4 is provisioned.

    Terminal
    $ terraform apply tfplan
Apply complete! Resources: 11 added, 0 changed, 0 destroyed.

Outputs:
instance_id = "i-086381ab281249fa1"
public_ip   = "54.89.144.201"
ssh_command = "ssh -i ~/.ssh/phase1-key ubuntu@54.89.144.201"

8. Production Failures, Forensics, and Triage

DevOps expertise is measured by how fast you triage and fix outages. Here are three real scenarios you will encounter:

Scenario 1: The 0.0.0.0/0 Security Breach Audit

Symptom

A junior engineer edits terraform.tfvars and sets my_ip = "0.0.0.0/0" to "make testing easier from anywhere". Within 1 hour, AWS Security Hub raises a Critical Finding: [PCI.EC2.6] Security groups should not allow ingress from 0.0.0.0/0 to port 22. Meanwhile, /var/log/auth.log shows thousands of failed SSH logins per minute.

View Diagnostic Steps & Immediate Triage

Step 1: Check live auth log on the server

EC2 Bash
$ sudo tail -n 20 /var/log/auth.log | grep "Failed password"
Failed password for invalid user root from 185.220.101.5 port 49202 ssh2
Failed password for invalid user admin from 194.26.29.112 port 51234 ssh2
Failed password for invalid user test from 45.154.255.89 port 38101 ssh2

Step 2: Remediate immediately in Terraform

terraform.tfvars
# Re-lock to operator /32 immediately
my_ip = "197.210.45.12/32"

Step 3: Apply the in-place Security Group update

Terminal
$ terraform apply -auto-approve
aws_security_group.ec2: Modifying... [id=sg-0a12b34c56d78e]
Apply complete! Resources: 0 added, 1 changed, 0 destroyed.

Because Security Group rule modifications are non-destructive in-place updates, existing valid SSH sessions remain open, but all unauthorized connections are severed immediately at the AWS packet boundary.

Scenario 2: The Gateway Blackhole Outage

Symptom

Terraform creates the VPC, Subnet, and EC2 instance successfully. The output shows public_ip = "54.89.144.201". But when you run ssh ubuntu@54.89.144.201, the connection hangs indefinitely: ssh: connect to host 54.89.144.201 port 22: Connection timed out.

View Root Cause & Route Table Forensics

Root Cause: The subnet was created, but the aws_route_table_association resource was omitted or commented out! When a subnet has no explicit association, it falls back to the VPC's Main Route Table, which by default only has a local route (10.0.0.0/16 -> local) and NO route to the Internet Gateway.

Diagnostic CLI Check:

AWS CLI
$ aws ec2 describe-route-tables --filters "Name=vpc-id,Values=vpc-0123456789abcdef" \
    --query "RouteTables[].Routes"
[
    { "DestinationCidrBlock": "10.0.0.0/16", "State": "active", "GatewayId": "local" }
]
# Notice: No 0.0.0.0/0 route pointing to igw!

Fix: Verify that both aws_route_table and aws_route_table_association exist in main.tf:

main.tf
resource "aws_route_table_association" "public" {
  subnet_id      = aws_subnet.public.id
  route_table_id = aws_route_table.public.id
}

Scenario 3: State Desynchronization and Phantom Drift

Symptom

A systems administrator logged into the AWS Web Management Console and manually added port 80 (HTTP) to the Security Group for testing. Later, when you run terraform plan, Terraform unexpectedly reports that the security group has drifted and wants to strip port 80.

View Drift Resolution Strategy

This is classic Configuration Drift. In GitOps, the code in Git is the single source of truth. Manual console changes are "ghost configurations".

You have two choices:

  1. Overrule and revert manual drift: Run terraform apply. Terraform will contact AWS and remove the rogue port 80 rule, enforcing the declared infrastructure state.
  2. Codify the change in Git: If port 80 was legitimately needed, add it to phase1/main.tf in code, commit to Git with Conventional Commits (feat(infra): open http port 80 on ec2 sg), and run terraform apply.
Terminal — Drift Reversal
$ terraform plan
~ resource "aws_security_group" "ec2" {
    # (6 unchanged attributes hidden)
  - ingress {
      - cidr_blocks = ["0.0.0.0/0"]
      - from_port   = 80
      - protocol    = "tcp"
      - to_port     = 80
    }
  }
Plan: 0 to add, 1 to change, 0 to destroy.

10. Hands-on Muscle Memory Exercises

  1. Inspect the Terraform Dependency Graph

    Run terraform graph in phase1/. You can pipe it to Graphviz (dot -Tpng -o graph.png) to visualize the exact dependency tree connecting the VPC, IGW, Route Table, Subnet, and Security Group.

  2. Query VPC State with AWS CLI

    Run aws ec2 describe-vpcs --filters "Name=tag:Name,Values=phase1-dev-vpc" --query "Vpcs[0].[VpcId,CidrBlock,State]". Verify that the CIDR block matches 10.0.0.0/16 and status is available.

  3. Verify Ingress Firewall Filtering

    Try running nmap -p 22 <public_ip> from a machine outside your /32 IP (e.g., your smartphone on cellular network). The port must report filtered (packets silently dropped), not open or closed!
